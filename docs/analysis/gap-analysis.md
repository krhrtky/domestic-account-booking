# ギャップ分析: カスタマージャーニーの問題点

## 概要

カスタマージャーニーを通じて特定された、機能間の整合性問題・UX課題・実装上のギャップを分析する。

---

## 重大度定義

| レベル | 定義 | 対応優先度 |
|--------|------|-----------|
| Critical | ジャーニーが進行不能になる | 即時対応 |
| High | ジャーニーは進行可能だが深刻なUX問題 | 次リリースまで |
| Medium | 軽微なUX問題または改善余地 | バックログ |
| Low | あれば便利な機能 | 検討 |

---

## 特定されたギャップ一覧

### GAP-001: 招待受け入れ時の確認ステップ欠如

| 項目 | 内容 |
|------|------|
| **重大度** | High |
| **フェーズ** | Phase 1 - 初期セットアップ |
| **ステップ** | ④ 招待受け入れ |
| **関連ファイル** | `app/invite/[token]/page.tsx` |

**現状**:
招待URL（`/invite/{token}`）にアクセスすると、自動的に招待が受け入れられ、ダッシュボードにリダイレクトされる。

**問題点**:
1. ユーザーが意図せず誤ったグループに参加してしまう可能性
2. 参加前にグループ情報（グループ名、招待者名等）を確認できない
3. 「参加しない」という選択ができない

**期待動作**:
1. 招待ページでグループ情報を表示
2. 「グループに参加する」ボタンで明示的に参加
3. 「キャンセル」ボタンで参加を拒否

**影響**:
- L-CX-003（エラーメッセージの明確性）に軽微に抵触
- ユーザーの予期せぬグループ参加リスク

---

### GAP-002: エラーメッセージの言語不統一

| 項目 | 内容 |
|------|------|
| **重大度** | Medium |
| **フェーズ** | 全フェーズ |
| **関連ファイル** | `app/invite/[token]/page.tsx`, `app/actions/group.ts` |

**現状**:
一部のエラーメッセージが英語で表示される。

**例**:
```typescript
// 英語メッセージ
return { error: 'User already belongs to a group' }
return { error: 'Invalid or expired invitation' }
<h1 className="...">Invalid Invitation</h1>

// 日本語メッセージ
return { error: 'グループに所属していません' }
return { error: '負担割合の合計は100%である必要があります' }
```

**問題点**:
- L-CX-003（エラーメッセージの明確性）違反
- L-LC-004（禁止表現）の精神に反する一貫性の欠如

**対応案**:
全エラーメッセージを日本語に統一

---

### GAP-003: 招待通知機能の不在

| 項目 | 内容 |
|------|------|
| **重大度** | Medium |
| **フェーズ** | Phase 1 - 初期セットアップ |
| **ステップ** | ③ 招待リンク発行 |
| **関連ファイル** | `app/actions/group.ts:invitePartner()` |

**現状**:
招待URLは画面に表示されるのみで、招待先へのメール送信機能がない。

**問題点**:
1. 招待者が手動でURLをコピー＆共有する必要がある
2. 共有方法によってはURLが切れたり改変される可能性
3. 招待されたことを被招待者が認識しづらい

**期待動作**:
1. 招待作成時にメール送信（オプション）
2. アプリ内通知機能

**対応案**（段階的実装）:
- Phase 1: 現状維持（URL共有方式）
- Phase 2: メール送信機能追加
- Phase 3: アプリ内通知

---

### GAP-004: 負担割合変更の遡及適用問題

| 項目 | 内容 |
|------|------|
| **重大度** | High |
| **フェーズ** | Phase 5 - 継続利用 |
| **ステップ** | 負担割合変更時 |
| **関連ファイル** | `app/actions/group.ts:updateRatio()`, `src/lib/settlement.ts` |

**現状**:
負担割合を変更すると、過去月の精算表示も新しい割合で再計算される。

**問題点**:
1. 過去に確定した精算額が変わってしまう
2. 「先月は60:40で精算したのに、表示が変わった」という混乱
3. 精算履歴のトレーサビリティ（L-BR-007）に影響

**例**:
```
1月: 負担割合 50:50 で精算済み（花子→太郎 ¥10,000）
2月: 負担割合を 60:40 に変更

→ 1月の精算表示が ¥10,000 から ¥6,000 に変わる（再計算）
→ しかし実際には¥10,000を送金済み
```

**期待動作**:
1. 精算確定時点の負担割合をスナップショットとして保存
2. 過去月は当時の割合で表示
3. 新しい割合は変更後の月から適用

**対応案**:
- 取引テーブルに `applied_ratio_a`, `applied_ratio_b` 列を追加
- または `settlements` テーブルを作成して確定情報を保存

### GAP-005: 単独利用時のUX課題

| 項目 | 内容 |
|------|------|
| **重大度** | Low |
| **フェーズ** | 全フェーズ |
| **関連ファイル** | 各コンポーネント |

**現状**:
パートナー未参加時でもアプリは動作するが、UIが2人前提で設計されている。

**問題点**:
1. 「ユーザーB」という表示が残る
2. 精算結果に意味がない（1人では精算対象がない）
3. 負担割合の意味が不明確

**例**:
```
User Bの支払い: ¥0
→ 太郎が太郎に¥50,000支払う（意味不明）
```

**期待動作**:
1. パートナー未参加時は「パートナーを招待してください」メッセージ
2. 精算表示を非表示または「パートナー参加後に表示」
3. 家計簿としての集計機能のみ提供

**対応案**:
- `user_b_id === null` 時の分岐表示を追加

---

### GAP-006: 取引詳細編集機能の不在

| 項目 | 内容 |
|------|------|
| **重大度** | Medium |
| **フェーズ** | Phase 3 - 明細仕分け |
| **関連ファイル** | `src/components/transactions/TransactionRow.tsx` |

**現状**:
取引の以下の項目が編集不可:
- 日付
- 金額
- 摘要（説明文）

**問題点**:
1. CSVインポート時の誤りを修正できない
2. 日付ミスがあると削除→再インポートが必要
3. 摘要を分かりやすく書き換えられない

**期待動作**:
1. 各フィールドをインライン編集可能に
2. または「編集」ボタンでモーダル表示

**対応案**:
- 取引編集用のServer Action追加
- TransactionRowに編集モード追加

---

### GAP-007: 日付フォーマットの不統一

| 項目 | 内容 |
|------|------|
| **重大度** | Low |
| **フェーズ** | 全フェーズ |
| **関連ファイル** | 各コンポーネント |

**現状**:
日付表示フォーマットが場所によって異なる。

**例**:
```
取引一覧: 2025-01-15（ハイフン区切り）
精算サマリー: 2025年01月（日本語）
CSVエクスポート: 2025/01/15（スラッシュ区切り）
```

**問題点**:
- L-CX-002（UI表示の一貫性）に軽微に抵触
- ユーザーの認知負荷

**期待動作**:
- すべて `YYYY年MM月DD日` または `YYYY/MM/DD` に統一

**対応案**:
- `src/lib/formatters.ts` に日付フォーマット関数を集約
- 全コンポーネントで共通関数を使用

---

### GAP-008: CSV重複インポート警告の不在

| 項目 | 内容 |
|------|------|
| **重大度** | Medium |
| **フェーズ** | Phase 2 - データ取り込み |
| **ステップ** | ⑤ CSV取り込み |
| **関連ファイル** | `src/lib/csv-parser.ts`, `app/actions/transactions.ts` |

**現状**:
同一CSVを複数回インポートすると、重複したトランザクションが作成される。

**問題点**:
1. 同じ取引が二重計上される
2. 精算金額が誤る
3. L-BR-006では重複検出が要件だが未実装

**期待動作（L-BR-006準拠）**:
1. 日付+金額+摘要で重複を検出
2. 重複がある場合は警告を表示
3. ユーザーがインポート続行/キャンセルを選択

**対応案**:
- インポート前にDB検索で重複チェック
- プレビュー画面で重複候補を表示
- 「それでもインポート」オプションを提供

---

### GAP-009: オンボーディングガイダンスの不足

| 項目 | 内容 |
|------|------|
| **重大度** | Medium |
| **フェーズ** | Phase 1 - 初期セットアップ |
| **関連ファイル** | `app/settings/page.tsx`, `app/dashboard/page.tsx` |

**現状**:
新規ユーザーがログイン後、何をすべきか明示されていない。

**問題点**:
1. グループ未作成状態でダッシュボードにアクセスすると中途半端な表示
2. 次に何をすべきか不明確
3. 初回利用時のチュートリアルがない

**期待動作**:
1. グループ未作成時は設定ページへ誘導
2. ステップバイステップのセットアップウィザード
3. 初回ダッシュボード表示時にガイド表示

**対応案**:
- オンボーディングコンポーネント追加
- ユーザーの進捗状態に応じたガイダンス

---

### GAP-010: 精算完了ステータス管理の欠如

| 項目 | 内容 |
|------|------|
| **重大度** | Low |
| **フェーズ** | Phase 4 - 精算確認 |
| **ステップ** | ⑫ 送金後 |
| **関連ファイル** | 該当なし（機能未実装） |

**現状**:
精算後に「精算完了」をマークする機能がない。

**問題点**:
1. どの月が精算済みか分からない
2. 精算履歴の管理ができない
3. 「この月はもう送金した」の記録がない

**期待動作**:
1. 月ごとに「精算済み」ボタン
2. 精算済みの月は視覚的に区別
3. 精算履歴一覧

**備考**:
REQUIREMENTS.mdで「精算の完了/未完了のステータス管理機能は不要（結果表示のみで良い）」と明記されているため、現状は仕様通り。
将来的な機能拡張として検討。

## 対応優先度

### 即時対応推奨（High）

1. **GAP-004**: 負担割合変更の遡及適用
   - 過去の精算データの整合性に影響
   - データモデル変更が必要

2. **GAP-001**: 招待受け入れの確認ステップ
   - UX改善で対応可能
   - 実装コスト低

### 次リリースで対応（Medium）

3. **GAP-002**: エラーメッセージ日本語化
4. **GAP-008**: CSV重複チェック
5. **GAP-006**: 取引詳細編集
6. **GAP-009**: オンボーディング改善
7. **GAP-003**: 招待通知機能

### バックログ（Low）

8. **GAP-007**: 日付フォーマット統一
9. **GAP-005**: 単独利用時UX
10. **GAP-010**: 精算完了ステータス

---

## 結論

カスタマージャーニーは基本的に**進行可能**であり、Critical（進行不能）なギャップはない。

主要な課題は:
1. **データ整合性**: 負担割合変更時の過去データ取り扱い（GAP-004）
2. **UX一貫性**: エラーメッセージ・日付フォーマットの不統一
3. **ユーザー導線**: オンボーディング・招待フローの改善余地

MVPとしては十分な完成度であり、上記ギャップは段階的に改善可能。
